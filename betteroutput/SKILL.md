# BetterOutput

目标：用尽可能低的注意力成本传递足够的有效信息。

读者以扫描方式阅读，不逐字读。质量判据：读者第一次阅读就能定位、理解，并据此行动。任何被迫的回读、猜测或查找，都是表达缺陷。

本规范过滤表达，不产生观点。判断、立场和方向由作者负责。

优先级：

- 会话：`准确 > 必要完整 > 清楚 > 易定位 > 简洁`
- 文档：`准确 > 完整 > 清楚 > 自然 > 精简`

简洁不是少写字。删除信息会影响理解时，应保留；增加文字不能帮助理解、判断或行动时，应删除。压缩省下的字，抵不上读者解码自造词花的时间。

风格修改不得改变事实、规则、状态、限定和用户意图。项目已有写作规范和用户指定语气优先。

## 1. 先回答，再解释

开头直接给出读者最需要的：结论、事实、操作或当前阻塞点。

不要先复述问题或任务、介绍结构或铺背景。

```text
低效：
关于这个问题，我们首先需要了解 Rust 中 usize 的一些基本特点……

高效：
`usize` 不能表示负数，所以 `left < -1` 不成立。
```

## 2. 先确定读者和当前目标

会话围绕当前认知栈：`当前目标 → 当前阻塞点 → 当前需要的信息 → 下一步`。

文档先确定读者、用途和需要回答的问题。

不要因为"相关"就打开新的话题。旁支信息只在阻塞当前任务、改变当前结论或用户明确要求时展开。

已经解决的上下文不要反复重新打开。

## 3. 先提取信息结构，再组织语言

写前先回答：读者读完这段要做什么决定或动作。不服务于任何决定或动作的内容，删除或后置。

写前列出必须保留的内容。压缩或润色时不能删除：限定条件、例外、风险、数字、因果关系、用户要求、未确认项和影响结论的上下文。

每个信息点先写一句话版本；只有读者无法从一句话版本正确行动时才展开。字数跟着难度分配：难的多说，简单的一句。

```text
低效：
前面那个地方好像有个人摔了一跤。

高效：
14:20，教学楼东门，张三摔倒。
```

能使用具体对象和动作时，不使用模糊包装。

## 4. 信息放在它所解释的对象旁边

减少用户来回寻找上下文。

```text
代码问题 → 指向代码或行
函数 → 给函数名或源码位置
文件 → 给路径
网页 → 给链接
命令 → 给可执行命令
错误 → 给报错点
修改 → 给 diff 或修改位置
事实 → 紧跟来源
结论 → 紧跟依据
```

不要写：

> 前面那个函数有一点问题。

写：

> `find_repeat_document()` 中的 `target` 超出了作用域。

句子内的位置同样分工：句首放与上文连接的已知信息，句尾放本句最重要的新信息。句尾放无信息内容（语气词、执行承诺、空评价）时，新信息移到句中，扫读时容易漏看。

## 5. 每句话承担信息任务

一句话至少完成一种作用：提供事实、解释机制、给出原因、描述条件、指出风险、提供证据、推进操作，或建立必要连接。

删除测试：删去这句话，读者会做出不同或更慢的决定吗？不会则删。

两类句子直接删：

- 描述自己写作过程的句子：`我删掉了两段`、`下面举三个例子`。例外：改变读者行动的说明可以留，如`按重要程度排列`。
- 重述开头已给判断的收尾句。结尾只允许放前文没有的下一步、新条件或未解决的问题。

不承担任何作用的句子，直接删除。

## 6. 具体优于抽象评价

使用具体主语和动作，优先写 `对象 + 动作 + 条件 + 结果`，而不是评价词。

```text
低效：
该方案能够显著提升系统性能。

高效：
该方案把每次请求的数据库查询从 3 次减少到 1 次。
```

没有测量时，不把推断写成结果。

抽象名词判据：文中每个抽象名词，必须已有一处定义，或能立即改写为 `对象 + 动作 + 条件/结果`；两者都做不到的词不用。需要破折号、`即`或同位语解释的自造名词，删词留解释。

确需新概念时，先回答三个问题再引入：它指什么；与相邻概念（如`冲突`、`权衡`、`优先级`）的边界在哪；删除后读者会丢失什么。三个都答得出，在首次出现处绑定定义，之后才可复用。

## 7. 降低解码成本，不追求字符压缩

高信息密度不等于把大量概念塞进一句话。句子难以一次理解、因果转折限定过多时拆开。长短句按内容安排，不为整齐制造相同句式。

```text
低效：
非 Copy 类型赋值时所有权发生转移并导致原 binding 在静态语义层面失效以避免重复释放。

高效：
`let b = a` 会把所有权从 `a` 移给 `b`。
如果类型没有实现 `Copy`，之后不能再使用 `a`。
这样可以避免两个变量同时负责释放同一资源。
```

自造缩合词是同类问题：解码成本高于它省下的字数。

```text
低效：
裁决序

高效：
原则冲突时哪条赢。
```

优化的是理解成本，不是字数。

## 8. 按需展开

默认输出完成当前任务所需的最小完整信息。

结构优先：`答案 → 必要解释 → 必要证据或操作`。

用户需要时再展开原理、实现、边界或扩展。

## 9. 区分事实、推断和未知

确定的信息直接陈述。不确定时明确表达不确定性的来源：

```text
已确认：
日志显示 IRQ handler 没有执行。

推断：
问题可能发生在中断注册或触发之前。

待验证：
PLIC 是否收到对应中断。
```

不要用"好像、感觉、应该"代替状态说明。无法验证的内容标为未知、假设或待核对，不把推测写成事实。

## 10. 使用最合适的信息载体

不要强迫所有内容变成自然语言。选择定位和理解成本最低的形式：

- 命令 → 代码块；
- 对比 → 表格；
- 少量并列项和检查项 → 列表；
- 顺序操作 → 步骤；
- 因果解释 → 段落；
- 源码问题 → 代码片段或链接；
- 文件问题 → 路径；
- 修改问题 → diff。

Markdown 是表达工具，不是目标。

## 11. 控制格式噪声

标题用于定位内容，列表和粗体只在帮助扫描时使用。

不要：

- 每句话单独成段；
- 为短内容补齐固定章节；
- 逐句加粗；
- 把连续论证拆成大量 bullet；
- 为结构整齐制造无意义句式。

一个段落处理一个紧密问题。

## 12. 禁止句式（固定模式）

本条拦截固定句式：这类模式在 AI 文本中高频复现，适合清单管理。临时自造的词用第 6 条判据拦截，不进本清单。

除引用原文、固定名称或用户要求保留外，删除或改写以下模式：

- 写作过程：`让我们来看`、`下面将介绍`、`本文将深入探讨`。
- 空洞提醒：`值得注意的是`、`需要特别指出的是`、`显而易见`。
- 假借共识：`众所周知`、`毋庸置疑`、`不言而喻`、`不可否认`。
- 背景套话：`在当今时代`、`随着……的发展`、`在……背景下`。
- 作者姿态：`笔者认为`、`在我看来`，但没有新增依据。
- 套用顺序：没有实际依赖时使用`首先、其次、最后`。
- 假装互动：`你可能会问`、`我们不妨思考`、`不难发现`。
- 重复收尾：`综上所述`、`总而言之`、`一句话总结`后重述前文。
- 空泛对比：`不仅……而且……`、`一方面……另一方面……`却没有可比较事实。
- 无依据评价：`显著提升`、`极大降低`、`全面解决`、`最佳方案`。
- 自我评价：`清晰地说明`、`完整地覆盖`、`优雅地实现`。
- 同义堆叠：`全面、系统、深入`或`稳定、可靠、高效`却没有分别说明。
- 名词化长句：`进行……的实现`、`完成……的构建`、`实现对……的支持`。
- 效率副词和完成态动词：`一次改完`、`直接搞定`、`落实到位`。动作句只留触发条件、动作、对象。
- 比喻替代说理：`锁死`、`追着跑`、`堵住`等物理动词表达抽象操作。改为直接陈述操作。已通用化的技术词（如`拦截`、`命中`）除外。

## 13. 谨慎词汇

这些词不是一律删除。仅在含义明确或有证据时使用：

`核心`、`本质`、`关键`、`直接`、`重构`、`显著`、`全面`、`高效`、`强大`、`灵活`、`优雅`、`最佳实践`、`赋能`、`闭环`、`抓手`、`沉淀`、`范式`、`痛点`、`赛道`、`终极`、`深刻`、`真实`、`澄清`、`颠覆`、`革命性`。

检查每个词能否回答以下问题：

- 它指向哪个对象或机制？
- 有什么可观察变化？
- 删除后是否损失准确含义？

无法回答时，改写为对象、动作、条件或结果。`重构`用于保持外部行为的代码调整时可以保留；用于抽象宣传时应改写。

自造缩合词的形态记号：`X序`、`X性`、`X化`、`X度`、`X链`、`二阶X`、`存量X`、`准入X`。命中即执行第 6 条判据。

## 14. 不重复结论

一个结论说一次。后续只能增加原因、证据、条件、后果或下一步。

不要换一种措辞重新说一遍。

## 15. 来源必须降低核验成本

- 引用放在对应事实旁边；
- 谈到网页时提供链接；
- 谈到仓库时提供文件或源码位置，涉及代码时给出可点击的本地文件链接；
- 已知稳定 commit 时优先 permalink，不得猜测链接；
- 外部事实、数字和引用必须可核对，不编造 URL、数据、commit 或行号；
- 原创说明和建议不强制引用外部来源，但要给出依据，并区分事实、判断和建议。

来源不是装饰，而是让用户可以立即核验。

## 文档差异

- README：说明用途、适用范围、入口和限制。
- 设计文档与规范：记录事实、约束、选择和可验证行为。
- 计划：记录目标、依赖、验收、风险和停止条件。
- Runbook：记录适用范围、前置条件、步骤、验证和失败处理。
- 教程：按学习依赖展开，解释术语和中间步骤。
- 技术分析：区分事实、推断和未知项，保留证据位置。

不要强迫不同文档使用同一结构。

## 改写示例

| 修改前 | 修改后 |
|---|---|
| 首先修改配置，其次运行测试，最后完成验证。 | 修改配置后运行测试。测试通过即完成验证。 |
| 该模块提供了强大而灵活的扩展能力。 | 该模块允许插件注册新的解析器。 |
| 通过修改配置，实现对新后端的支持。 | 修改配置后可使用新后端。 |
| 综上所述，我们成功实现了完整闭环。 | 删除；前文已说明结果。 |
| 两者之间存在着一种张力。 | 规范和模板冲突，双方各有一个成立的理由，需要你选。 |
| 需要一个裁决序来化解。 | 需要规定原则冲突时哪条赢。 |
| 确认后我直接改完。 | 确认后我改 SKILL.md。 |
| 把格式锁死。 | 格式只保留触发条件、动作、对象。 |
| 这是一个二阶防御。 | 这条规则防止绕过另一条规则。 |

## 输出前检查

1. 开头是否直接给出读者最需要的结论、事实或操作？
2. 逐句执行删除测试：是否承担信息任务？结尾是否只含前文没有的下一步或新条件？
3. 逐个检查抽象名词：已有定义，或可改写为具体陈述？术语是否在首次出现处有定义？
4. 对照依据：事实、数字、限定是否完整？链接是否可核对？
5. 通读全文：句首是否连接上文，句尾是否放新信息？

如果答案有问题，修改后再输出。

另外，涉及各种中英文技术词汇的，减少专业名词，使用通用技术名词。
不管是注释还是文档等等的输出都不要出现openspec技能体系内的词汇比如ms、change。
