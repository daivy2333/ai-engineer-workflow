# BetterMd

按此顺序取舍：准确 > 完整 > 清楚 > 自然 > 精简。

风格修改不得改变事实、规则、状态或用户意图。项目已有写作规范和用户指定语气优先。

## 写作规则

1. 先确定读者、用途和需要回答的问题。
2. 先列出必须保留的事实、数字、条件、原因、风险和未确认项。
3. 开头给出读者需要的结果或事实，不复述任务，不介绍写作过程。
4. 使用具体主语和动作。能写机制、变化或影响时，不写抽象评价。
5. 一个段落只处理一个问题。因果、转折或限定过多时拆句。
6. 长短句按内容安排。不要为了整齐制造相同句式。
7. 列表用于并列项、步骤和检查项。需要解释关系时使用段落。
8. 标题用于定位内容。不要为短内容补齐固定章节。
9. 粗体只标记需要扫描的信息。不要逐句加粗。
10. 结论说一次。后文补充证据、条件或后果，不换词重复。

## 信息与来源

- 原文润色必须保留有效信息。删除内容前确认它不是条件、例外、原因或证据。
- 外部事实、数字和引用必须可核对。不得编造 URL、数据、commit 或行号。
- 原创说明和建议不强制引用外部来源，但要给出依据，并区分事实、判断和建议。
- 涉及仓库代码时，给出可点击的本地文件链接。已知稳定 commit 时可使用 permalink，不得猜测链接。
- 无法验证的内容标为未知、假设或待核对，不把推测写成事实。

## 禁止句式

除引用原文、固定名称或用户要求保留外，删除或改写以下模式：

- 写作过程：`让我们来看`、`下面将介绍`、`本文将深入探讨`。
- 空洞提醒：`值得注意的是`、`需要特别指出的是`、`显而易见`。
- 假借共识：`众所周知`、`毋庸置疑`、`不言而喻`、`不可否认`。
- 背景套话：`在当今时代`、`随着……的发展`、`在……背景下`。
- 作者姿态：`笔者认为`、`在我看来`，但没有新增依据。
- 套用顺序：没有实际依赖时使用`首先、其次、最后`。
- 假装互动：`你可能会问`、`我们不妨思考`、`不难发现`。
- 重复收尾：`综上所述`、`总而言之`、`一句话总结`后重述前文。
- 空泛对比：`不仅……而且……`、`一方面……另一方面……`却没有可比较事实。
- 无依据评价：`显著提升`、`极大降低`、`全面解决`、`最佳方案`。
- 自我评价：`清晰地说明`、`完整地覆盖`、`优雅地实现`。
- 同义堆叠：`全面、系统、深入`或`稳定、可靠、高效`却没有分别说明。
- 名词化长句：`进行……的实现`、`完成……的构建`、`实现对……的支持`。

## 谨慎词汇

这些词不是一律删除。仅在含义明确或有证据时使用：

`核心`、`本质`、`关键`、`直接`、`重构`、`显著`、`全面`、`高效`、`强大`、`灵活`、`优雅`、`最佳实践`、`赋能`、`闭环`、`抓手`、`沉淀`、`范式`、`痛点`、`赛道`、`终极`、`深刻`、`真实`、`澄清`、`颠覆`、`革命性`。

检查每个词能否回答以下问题：

- 它指向哪个对象或机制？
- 有什么可观察变化？
- 删除后是否损失准确含义？

无法回答时，改写为对象、动作、条件或结果。`重构`用于保持外部行为的代码调整时可以保留；用于抽象宣传时应改写。

## 文档差异

- README：说明用途、适用范围、入口和限制。
- 设计文档与规范：记录事实、约束、选择和可验证行为。
- 计划：记录目标、依赖、验收、风险和停止条件。
- Runbook：记录适用范围、前置条件、步骤、验证和失败处理。
- 教程：按学习依赖展开，解释术语和中间步骤。
- 技术分析：区分事实、推断和未知项，保留证据位置。

不要强迫不同文档使用同一结构。

## 改写示例

| 修改前 | 修改后 |
|---|---|
| 值得注意的是，该方案能够显著提升性能。 | 该方案减少一次数据库查询。性能变化尚未测量。 |
| 首先修改配置，其次运行测试，最后完成验证。 | 修改配置后运行测试。测试通过即完成验证。 |
| 该模块提供了强大而灵活的扩展能力。 | 该模块允许插件注册新的解析器。 |
| 通过修改配置，实现对新后端的支持。 | 修改配置后可使用新后端。 |
| 综上所述，我们成功实现了完整闭环。 | 删除；前文已说明结果。 |

## 审查改写

完成前执行：

1. 对照原文或依据，确认事实和限定没有丢失。
2. 删除任务复述、过程说明和重复结论。
3. 把抽象评价换成对象、机制、结果或证据。
4. 检查标题、列表和粗体是否帮助阅读。
5. 扫描禁止句式，复核谨慎词汇。
6. 检查术语、数字、链接和代码位置。
7. 通读全文，修正机械重复的句式和节奏。
