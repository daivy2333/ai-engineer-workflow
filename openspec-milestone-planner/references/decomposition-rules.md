# Milestone 拆分规则

Milestone 是有工作量的可调试阶段。它完成后应形成新的稳定基线，而不是只完成一次局部修改。

## 合适的范围

每个 milestone 同时满足：

- 只有一项阶段成果。
- 包含一组相互依赖的工作。
- 单独完成后具有项目价值。
- 不依赖后续阶段即可验证。
- 失败时能限制排查范围。
- 后续阶段可以依赖其稳定结果。

一个 milestone 可以由多个 change 完成。change 数量不决定 milestone 数量。

## 需要合并

出现以下情况时，优先与相邻 milestone 合并：

- 只修改一个函数、接口或配置。
- 只增加测试、日志或观测点。
- 只完成某项能力的内部步骤。
- 完成后没有新的稳定基线。
- 与相邻项共享相同成果、验证和诊断边界。

高风险基础验证可以单独存在。例如首次证明中断能重复投递，虽然代码量小，但它建立了后续工作的故障边界。

## 需要拆分

出现以下情况时继续拆分：

- 标题包含可独立成立的多个成果。
- 同时涉及多个互不依赖的故障域。
- 需要多组无关验证才能判断完成。
- 阶段中途存在可独立复用的稳定状态。
- 一部分失败后，其他部分仍能独立成立。
- 同时混入 bring-up、功能、性能和清理。

跨模块不自动意味着过重。若模块共同形成同一个可验证集成结果，可以保留在同一 milestone。

## 审计问题

聚合审计：

1. 单独完成后，项目获得了什么？
2. 该结果能否成为后续工作的前置条件？
3. 它是否只是相邻阶段的一项内部任务？
4. 合并后是否仍保留清晰的故障边界？

拆分审计：

1. 是否存在两个可分别验收的结果？
2. 失败时是否需要检查多个独立系统？
3. 是否能在中途建立稳定检查点？
4. 是否有一部分可以独立延期或回退？

## 示例

过粗：

```text
MS01 完成整个设备驱动
```

过细：

```text
MS01 增加 RX ring
MS02 注册 waker
MS03 修改中断使能位
```

较合适：

```text
MS01 建立轮询模式下可重复验证的收发基线
MS02 建立可重复触发和诊断的中断路径
MS03 建立异步收发与唤醒路径
MS04 建立 drain、并发和错误恢复语义
MS05 完成目标平台的稳定性与性能验证
```

示例只说明拆分方法，不规定固定阶段数量。
